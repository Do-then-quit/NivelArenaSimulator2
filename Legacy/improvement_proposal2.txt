✦ 제공된 소스코드와 카드 데이터(BT01~05, ST01~09, SB01)를 분석한 결과, 현재 프로젝트는 초기 구축 단계(ST01~03, BT01
  일부)를 넘어 중반부 메커니즘을 수용하기 위한 과도기에 있습니다.

  앞으로 남은 카드팩들을 완벽하게 구현하기 위해 현재 프로젝트에서 보완, 개선, 또는 새롭게 추가해야 할 기능들을 분석하여
  정리해 드립니다.

  ---

  1. 누락된 핵심 키워드 및 메커니즘 구현 (Rule/Engine 레벨)

  현재 GameEngine과 types.ts에는 기본적인 키워드(어태커, 디펜더 등)는 있으나, 후반부 팩(BT02 이후)에 등장하는 복합적인
  키워드에 대한 처리가 부족합니다.

   * 이스케이프 (Escape) [BT05, ST08, ST09]
       * 현황: types.ts에 정의되지 않음.
       * 필요 기능: "자신의 메인 페이즈가 시작할 때"라는 트리거가 필요합니다. 현재 GameEngine.ts의 nextPhase는 페이즈만
         변경하고 즉시 사용자 입력 대기로 넘어갑니다.
       * 개선안: Phase.MAIN 진입 직후 ActivationCondition.PHASE_START 같은 조건을 신설하여, 자동으로 발동하는 효과(덱 맨
         아래로 이동 후 드로우 등)를 처리하는 로직이 필요합니다.
   * 믹스 (Mix) [BT05, ST09]
       * 현황: 속성 참조 로직 부재.
       * 필요 기능: "자신의 필드에 특정 속성 이외의 카드가 있는지" 확인하는 조건이 필요합니다.
       * 개선안: EffectCondition 타입에 MIX_CONDITION 또는 ATTRIBUTE_VARIETY를 추가하고, EffectManager에서 필드 유닛들의
         속성을 검사하는 로직을 추가해야 합니다.
   * 크레딧 (Credit) [ST08, ST09]
       * 현황: 별도 키워드 처리 없음.
       * 필요 기능: 배치 시(Entry)와 트래시 시(Exit) 두 가지 타이밍에 각각 드로우/패 버리기 효과가 강제됩니다.
       * 개선안: CardDatabase에서 데이터를 로딩할 때 Credit 키워드가 감지되면 자동으로 ENTRY와 EXIT 효과를 주입해주는
         팩토리 함수가 필요합니다.
   * 유니크 (Unique) 아이템 [BT02]
       * 현황: 아이템 장착 로직(RuleValidator.canPlayItem)에 수량 제한 로직이 없음.
       * 필요 기능: 특정 유닛이나 필드 전체에 동일한 이름의 유니크 아이템 장착 제한 구현.
   * 성약 / 맹세 (Covenant/Oath) 제약 [BT04]
       * 현황: 특정 특성을 가진 카드를 사용한 턴에 제약을 거는 로직 부재.
       * 필요 기능: PlayerState에 flags나 constraints 객체를 추가하여 "이번 턴에 성약 스킬 사용 불가" 등의 상태를
         관리해야 합니다.

  2. 구체적인 액션 및 타겟팅 기능 확장

  effectActions.ts와 TargetSelector.ts는 현재 단순한 대상 지정만 지원합니다. 복잡한 효과를 위해 확장이 필요합니다.

   * 덱/트래시 조작의 고도화
       * 덱 조작: "덱 맨 아래로 되돌리기" (이스케이프, 믹스 효과 등), "덱에서 특정 카드 서치" (크라운 BT05-006 등)
         기능이 필요합니다. 현재는 REVEAL_TOP 정도만 있습니다.
       * 대미지 존 조작: BT04(레테 등)부터 대미지 존의 카드를 참조하거나, 대미지 존으로 카드를 보내거나
         가져오는(회복/자해) 효과가 많습니다. 현재는 단순히 대미지를 입는 dealDamage만 존재합니다. MOVE_TO_DAMAGE_ZONE,
         PICK_FROM_DAMAGE_ZONE 액션이 필요합니다.
   * 아이템 관련 심화 로직
       * 비용 참조: "장착한 아이템의 코스트 합" 또는 "장착한 아이템 수"를 참조하는 로직이 필요합니다 (BT05 에이드 등).
       * 장착 해제/이동: "장착한 아이템을 패로 되돌리거나 트래시"하는 액션이 필요합니다.
   * 스킬 존 상호작용
       * BT03(라피: 레드 후드) 등은 스킬 존에 있는 카드를 트래시하고 효과를 발동합니다. 현재 스킬 존은 사용된 스킬이
         잠시 머무는 곳으로만 구현된 것으로 보이나, 실제 게임에서는 지속물처럼 쓰이거나 비용으로 사용될 수 있으므로
         SELECT_SKILL_ZONE_TARGET 기능이 필요합니다.

  3. UI/UX 개선 필요 사항

  시뮬레이터로서 사용자 경험을 위해 추가되어야 할 UI 요소들입니다.

   * 덱/트래시/대미지 존 확인 UI:
       * 유저가 언제든지 자신의 덱 남은 매수, 트래시 내용물, 대미지 존의 카드를 확인할 수 있는 팝업이나 패널이
         필요합니다. 특히 서치 효과나 대미지 존 참조 효과를 위해 필수적입니다.
   * 선택 모드의 다양화:
       * 현재는 SELECT_TARGET 하나로 퉁쳐져 있으나, "덱에서 선택", "대미지 존에서 선택", "스킬 존에서 선택" 등 선택
         출처를 명확히 구분하여 UI를 띄워야 합니다.
   * 자동 효과 체인 시각화:
       * 트리거가 연쇄적으로 발생하거나, 선택 효과(Optional)가 떴을 때 유저가 흐름을 이해할 수 있도록 스택(Stack)이나
         대기열 UI가 필요할 수 있습니다.

  4. 구조적 리팩토링 제안

   * EffectManager의 조건 검사 분리:
       * checkCondition 함수가 너무 비대해질 수 있습니다. ConditionValidator 클래스로 분리하여 '믹스', '전선구축',
         '레벨링크' 등의 복잡한 조건을 개별 함수로 관리하는 것이 좋습니다.
   * Phase State Machine 강화:
       * 현재 nextPhase 함수 내 스위치문으로 관리되는 페이즈 전환을 PhaseManager로 분리하고, 각 페이즈 진입(OnEnter) /
         종료(OnExit) 시점에 훅(Hook)을 걸 수 있게 구조를 변경해야 '메인 페이즈 시작 시' 같은 효과를 깔끔하게 처리할 수
         있습니다.

  5. 데이터 검증 (Data Validation)

   * JSON 데이터 파싱 강화:
       * 현재 keywords를 정규식으로 파싱하여 처리하고 있으나(CardDatabase.ts), BT01-019의 예시처럼 텍스트 내에 복잡한
         조건이 섞인 경우([1]) 파싱 오류가 발생할 수 있습니다. 키워드 파싱 로직을 더 견고하게 만들거나, JSON 데이터 구조
         자체를 더 구조화된 형태(Effect 객체 포함)로 마이그레이션 하는 것을 고려해야 합니다.

  요약: 우선순위별 작업 제안

   1. Engine: 페이즈 시작 트리거(PHASE_START) 추가 (이스케이프 구현용).
   2. Logic: MIX, CREDIT 조건 및 관련 로직 구현.
   3. Action: 대미지 존 조작(Heal, SelfDamage, SwapDamage) 및 덱 서치/조작 액션 구현.
   4. UI: 트래시/대미지 존/덱 확인 팝업창 구현.

  이 분석을 바탕으로, 우선적으로 BT04(대미지 존 조작, 성약)와 BT05(믹스, 이스케이프) 구현을 위한 엔진 확장을 진행하는
  것을 추천합니다.
